# 上传耗时测量

R9 计时已于 2026-10-31 随 `2b6f3e0` 发布，尚未完成生产采样，未做上传架构优化。用户 M-8 跳过审计账号实测后，又在 M-10 明确授权使用现有管理员上传六张测试图：公共路径仅上传草稿、不提交，另一条路径为该管理员自己的个人空间。两种尺寸在两条路径上均覆盖，测完仅删除这六张并核对数据恢复。本地约 200KB 和约 2MB 的六张样本保留；当前成功样本为零，浏览器登录再次失效。按 M-13 先完成七天会话配置，再交接登录、继续测速，不从失败的文件选择尝试推断上传耗时。

计时使用 `System.nanoTime()`，日志固定为 `upload_timing stage=<固定阶段> elapsed_ms=<毫秒> bytes=<字节数>`。阶段只接受枚举，不能传入文件名、用户 ID、地址、签名或异常。失败路径也记录耗时，不吞掉原异常、不重试上传。

| 阶段 | 测量范围 | 限制 |
| --- | --- | --- |
| RECEIVE_LOCAL | MultipartFile 写入 SDK 所需临时文件 | Servlet 已解析 multipart，不包含浏览器到服务器的网络传输 |
| RECEIVE_REMOTE | 服务端下载远程图片 | 失败时尚无完整文件，bytes 记 0，不代表未收过数据 |
| PREPARE_VARIANTS | 准备数据万象变体规则 | 不是云端压缩时间 |
| COS_UPLOAD | 每次 SDK putObject 调用 | 图片 PUT 含云端变体生成；含 SDK 内部重试，不拆解单次 HTTP 尝试 |
| PRIVATE_ACL | 每个预期私有派生对象的 ACL 确认 | 不含 PUT；bytes 为该变体大小 |
| DATABASE | 公共落库事务、私有 save 调用 | 含权限复查和事务内清理队列操作；私有失败时还含补偿登记；bytes 为入库展示图 picSize，可能小于原文件 |

当前上传把原图和数据万象规则放在同一次 COS PUT 中，云端生成展示图和缩略图。没有独立的本地压缩或逐变体 PUT；不能拆出不存在的独立耗时，也不能据此直接实施“多个变体并行上传”。M-4 已确认 CosManager 和既有落库方法的计时修改范围，以上阶段已接入，不改变业务返回值和异常行为。

真实站点采样将按顺序上传约 200KB 和约 2MB 图片各三次，记录每次端到端耗时、上述可测阶段及文件大小，整理到状态文件。以顺序、日志时间和线程辅助关联样本；计时本身不增加关联 ID，并发请求交错时不能可靠关联，应重新顺序采样。尚无生产测量结果，不从模拟测试推断性能改善。

本地验证（2026-10-31）：`mvn verify` 515 项，510 通过、5 条件跳过；新增 13 项覆盖日志格式及输入大小、失败接收、五种 COS 调用入口、私有 ACL 和公共/私有保存的成功与异常行为。前端单测 166 项、完整浏览器回归 104 项、类型检查、生产构建均通过，Gitleaks 工作区和历史扫描通过。测试没有连接生产桶或数据库。

## 上传路径分析（2026-10-31）

本次只读检查当前后端容器日志，没有发现 `upload_timing` 样本。因此以下是代码路径分析，不是已测得的瓶颈排序或提速结论。

- 本地文件接收写临时文件，然后读取 12 字节头部校验；不会为生成变体重复上传原始二进制。
- 原图和两条变体规则在一次 COS PUT 中提交。把它改成多个独立上传会改变流程，不能当作直接可用的并行优化。
- 私有上传成功后，对返回结果中匹配当前桶和预期输出键的变体逐一设置 `Private` ACL。通常有两次独立网络调用，可评估有界并行；必须保留全部校验，任一失败仍拒绝上传，并等所有已提交任务结束后才进入补偿，防止后台 ACL 写入与对象删除竞态。
- 公共废弃变体已经通过持久队列异步清理，没有可直接移走的同步 COS 删除等待。数据库保存包含上传凭据认领、权限复查和事务，不能为缩短计时跳过这些步骤。

监督意见 M-9 暂不同意 ACL 并行：尚无真实计时样本，收益不确定，而权限相关的并发失败处理会增加风险。因此不实施该候选，保持现有串行流程；后续先取得真实上传各阶段耗时，再按数据提出方案。本地模拟不能代替真实上传延迟数据，任何优化发布仍需收件箱中的用户原话。
