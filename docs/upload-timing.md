# 上传耗时测量

R9 计时已于 2026-10-31 随 `2b6f3e0` 发布，未做上传架构优化。用户 M-10 授权管理员在公共草稿和自己的个人空间上传六张测试图；浏览器自动文件选择未触发请求，后改由用户手动上传。M-17 告知上传完毕并反馈多文件拖入只出现一张。数据库和日志实际只有两张成功样本，已精确删除并恢复基线；不把两张写成完成六次采样，不自行补传。

计时使用 `System.nanoTime()`，日志固定为 `upload_timing stage=<固定阶段> elapsed_ms=<毫秒> bytes=<字节数>`。阶段只接受枚举，不能传入文件名、用户 ID、地址、签名或异常。失败路径也记录耗时，不吞掉原异常、不重试上传。

| 阶段 | 测量范围 | 限制 |
| --- | --- | --- |
| RECEIVE_LOCAL | MultipartFile 写入 SDK 所需临时文件 | Servlet 已解析 multipart，不包含浏览器到服务器的网络传输 |
| RECEIVE_REMOTE | 服务端下载远程图片 | 失败时尚无完整文件，bytes 记 0，不代表未收过数据 |
| PREPARE_VARIANTS | 准备数据万象变体规则 | 不是云端压缩时间 |
| COS_UPLOAD | 每次 SDK putObject 调用 | 图片 PUT 含云端变体生成；含 SDK 内部重试，不拆解单次 HTTP 尝试 |
| PRIVATE_ACL | 每个预期私有派生对象的 ACL 确认 | 不含 PUT；bytes 为该变体大小 |
| DATABASE | 公共落库事务、私有 save 调用 | 含权限复查和事务内清理队列操作；私有失败时还含补偿登记；bytes 为入库展示图 picSize，可能小于原文件 |

当前上传把原图和数据万象规则放在同一次 COS PUT 中，云端生成展示图和缩略图。没有独立的本地压缩或逐变体 PUT；不能拆出不存在的独立耗时，也不能据此直接实施“多个变体并行上传”。M-4 已确认 CosManager 和既有落库方法的计时修改范围，以上阶段已接入，不改变业务返回值和异常行为。

真实站点采样将按顺序上传约 200KB 和约 2MB 图片各三次，记录每次端到端耗时、上述可测阶段及文件大小，整理到状态文件。以顺序、日志时间和线程辅助关联样本；计时本身不增加关联 ID，并发请求交错时不能可靠关联，应重新顺序采样。尚无生产测量结果，不从模拟测试推断性能改善。

本地验证（2026-10-31）：`mvn verify` 515 项，510 通过、5 条件跳过；新增 13 项覆盖日志格式及输入大小、失败接收、五种 COS 调用入口、私有 ACL 和公共/私有保存的成功与异常行为。前端单测 166 项、完整浏览器回归 104 项、类型检查、生产构建均通过，Gitleaks 工作区和历史扫描通过。测试没有连接生产桶或数据库。

## 上传路径分析（2026-10-31）

本次只读检查当前后端容器日志，没有发现 `upload_timing` 样本。因此以下是代码路径分析，不是已测得的瓶颈排序或提速结论。

- 本地文件接收写临时文件，然后读取 12 字节头部校验；不会为生成变体重复上传原始二进制。
- 原图和两条变体规则在一次 COS PUT 中提交。把它改成多个独立上传会改变流程，不能当作直接可用的并行优化。
- 私有上传成功后，对返回结果中匹配当前桶和预期输出键的变体逐一设置 `Private` ACL。通常有两次独立网络调用，可评估有界并行；必须保留全部校验，任一失败仍拒绝上传，并等所有已提交任务结束后才进入补偿，防止后台 ACL 写入与对象删除竞态。
- 公共废弃变体已经通过持久队列异步清理，没有可直接移走的同步 COS 删除等待。数据库保存包含上传凭据认领、权限复查和事务，不能为缩短计时跳过这些步骤。

监督意见 M-9 暂不同意 ACL 并行：尚无真实计时样本，收益不确定，而权限相关的并发失败处理会增加风险。因此不实施该候选，保持现有串行流程；后续先取得真实上传各阶段耗时，再按数据提出方案。本地模拟不能代替真实上传延迟数据，任何优化发布仍需收件箱中的用户原话。

## 默认 ACL 核验（2026-11-01，M-20）

在独立随机测试前缀下 PUT 普通测试对象，不发送对象 ACL：PUT 200、签名 GET 200、匿名 GET 403。桶 ACL 查询返回 200，授予对象仅为桶所有者；桶策略查询返回 404、空响应体，不能据此声称已读取并逐项审计策略。精确删除探针返回 204，删除后签名 GET 404。首次探针因空策略响应的 XML 解析失败提前结束，也已在 finally 中删除并确认 404；修正解析后重新完成上述核验，无遗留测试对象。

本次没有去掉 ACL 调用：实际两次设置位于 `CosManager.putPrivatePictureObject`，作用于数据万象生成的展示图、缩略图，而本次普通对象探针没有覆盖派生处理路径。普通对象匿名 403 不能单独证明派生对象的默认权限；模拟 SDK 的单元测试也不能证明真实 COS 匿名访问受限。按 M-20“结论拿不准就不改”的要求，保留现有串行设置，不宣称提速或提交优化版本。

后续若要移除，应先取得派生对象未显式设置 ACL 时仍匿名 403 的真实证据，并确认桶策略；移除后派生对象私有性将依赖私有桶的默认权限。`CosManager` 非计时代码修改需补齐文件范围确认。上述后续核验及代码改动本次未执行，部署也未获授权。

## 派生对象核验与优化（2026-11-01，M-22）

M-22 补充授权 `CosManager` 的最小修改，以及核验明确、全量测试通过后的直接部署。以下为后续证据，更新上一节暂不修改的结论。

- 正式广州端点确认桶存在且地域为广州，桶 ACL 仅授权所有者；正式地域端点和加速端点的 `GET /?policy` 均返回 COS 的 404 空响应，表示策略资源未配置。没有把这个响应写成“200 读取策略正文”；没有修改桶 ACL 或策略。
- 使用与 `FileManager` 相同的 WebP 展示图（质量 85）和缩略图（512×512、质量 80）规则，上传 204682 字节 PNG，不设置原图或派生对象 ACL。两种预期派生图都实际生成，原图、展示图、缩略图签名 GET 全部 200，匿名 GET 全部 403，各对象 ACL 无公共授权。
- 三个探针对象按预先记录的精确 key 删除，DELETE 均 204，签名 GET 均 404。通用检查脚本再次执行也通过；M-23 再以 `--explicit-original-acl` 保留原图显式 Private、仅省略派生 ACL 的方式复测，三对象仍为签名 200 / 匿名 403 / 清理后 404，未产生业务图片记录。

改动仅移除上传成功后对两种派生图的 `setObjectAcl(Private)` 网络调用；原图 PUT 仍显式携带 `Private`，单次 PUT 的结果、异常传播、计时和失败补偿保持原样。**派生图私有性依赖独立私有桶的默认 ACL，不能将该桶改成公共读写，也不能用公开策略授予匿名读取。** 应用的原图和两种派生图读取接口仍要求身份和空间权限，新增三种变体的匿名拒绝回归；SDK 模拟单测验证原图私有 ACL 保留、没有额外 ACL 请求，不将模拟结果当作云端权限证据。

`scripts/check-private-cos-acl.py` 是显式触发的真实 COS 发布检查：需 Python `requests`、私有权限配置文件、独立私有桶和可丢弃 PNG 样本，使用 `--run-live --properties <配置文件> --private-bucket <私有桶> --fixture <PNG> --journal <恢复清单>`。脚本拒绝公共桶和公开授权，断言三个对象匿名 403、有权访问 200，并在 finally 中精确清理；只输出状态码与布尔结果，失败退出非零。加 `--explicit-original-acl` 可复现应用当前的原图 Private PUT。不要用 `python -O` 关闭断言。它会真实写入测试对象，运行前必须有对应授权，不加入普通离线单测。

历史 `PRIVATE_ACL` 数据保留其原口径；优化后的上传不再产生这两个阶段。不能仅把旧样本的 3353 毫秒从每次上传中扣除并承诺相同比例提速，部署后的真实样本需要另行记录。

本批本地验证：`mvn verify` 518 项（513 通过、5 项既有条件跳过、0 失败/错误），前端 175 单测、106 浏览器回归、类型检查、生产构建通过；Gitleaks 工作区及历史扫描无泄露。新增三项原图/展示图/缩略图匿名接口拒绝测试，真实 COS 权限结论来自上述显式运行的探针。
